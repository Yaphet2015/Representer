# PDF support: first vertical slice

## Decisions

| Decision | Source / reason |
|---|---|
| Browser side panel, original PDF untouched | User rejected a separate tab. Native PDF side-panel + local-worker extraction was verified in Chrome on the user's 59-page Lilly file (probe only). No default-reader replacement or navigation interception. |
| Existing settings canvas, 13px text, accent button, Overview renderer | Existing Representer design system is the direct-build reference. No new branding or imagery. Opening an authorized PDF sidebar starts local read → Overview (same cache, cancel, retry, and chat as the webpage overlay), with local source-page text. |
| Side panel only for a PDF document | Toolbar and shortcut share one router. Unknown documents are inspected with `scripting.executeScript` in the top frame: only a positive `document.contentType === 'application/pdf'` opens PDF UI, including extensionless URLs. No receiver, injection error, or HTTP(S) URL is not PDF evidence. Other positively inspected documents use the in-page overlay. If the webpage script is absent (for example, a tab predating installation), the packaged content script is injected into the inspected `documentId` before toggling, without refreshing or fetching the URL. Initialization ownership and invalidation cleanup prevent duplicate listeners. The new `scripting` permission uses existing `<all_urls>` host access. Confirmed PDF kind is session-scoped and invalidated on loading; late callbacks after navigation are ignored. Inspection, injection, or panel-open failures show a toolbar `!` badge and explanatory title, with bounded non-sensitive warning codes. `openPanelOnActionClick` stays false; HTML announcements disable only their own tab. Reported Chrome checks passed pre-install HTML recovery, newly opened HTML shortcuts, and initial native PDF MIME inspection/automatic reading. PDF shortcut reopening after closing the panel remains inconsistent and is not accepted as fixed. |
| Separate source context for Overview | No PDF paragraph is a DOM fingerprint. Block IDs map deterministically to PDF page numbers; repeated sentences cannot choose another page by fuzzy matching. No native-viewer highlight/jump claim. |
| Authorized sidebar starts Overview automatically | Opening a user-authorized PDF side panel fetches and parses that document locally, then starts an Overview with the configured model (cache reused, same as a webpage). There is no extra Read/Summarize click, and no background scan of other PDFs. Cancel, retry, regenerate, and missing-model errors follow the webpage overlay. Existing summary/chat background protocols still own model calls and cache writes; the local read path does not access model settings directly. |
| Dedicated `pdf:v1:` summary/session cache key | Never reuse a webpage DOM cache for a PDF at the same URL. No raw PDF byte persistence. |
| Session authorization, not a free URL fetch RPC | Only a real action's current tab URL is selected. Exact active-tab/canonical-URL/token checks before/after parsing and before model actions. Session storage survives worker suspension; navigation/reload/tab removal revokes. Thirty-minute expiry. No background fetch service. |
| Reject redirects, omit cookies, block known local URLs | Do not turn the extension into a credentialed or arbitrary cross-origin fetch proxy. This is not DNS resolution; public hosts resolving internally remain a limitation. |
| All pages, including image-only pages, or explicit failure | 64 MiB, 300 pages, 350k characters including markers, 90 seconds; no first-three-page production shortcut. Password protection still fails explicitly. Image-only and mixed empty pages are kept, listed, and flagged so the agent can inspect a rendering. Text items are joined with PDF.js in-flow geometry (0.102em), not by inserting a space after every item or by dictionary-merging fragments. |
| Lazy local PDF.js legacy bundle | No parser in content/options. Worker, standard fonts and CMaps stay local. No PDF scripting/action API is invoked. The service worker may lazy-load PDF.js only for an authorized visual session. Tables/reading order remain lossy and disclosed. |
| On-demand page images, not a single packed request | The complete PDF is available to the agent: every page's text (or a placeholder) plus a compact catalog of text/image flags. `inspect_pdf_page` renders one page at a time (bounded resolution, budget, in-memory LRU). Native `application/pdf` file parts are not used: the configured OpenAI-compatible adapter only documents `image_url` data URIs, and stuffing a large multi-page PDF in one request would break provider compatibility and memory bounds. Webpage turns stay text-only. A run can inspect at most 10 distinct pages; that cap is not renewable mid-run, and the sidebar reports the inspected page count so a partial run is not presented as full visual coverage. Vector charts may exist even when `hasImages` is false (that flag only means no image paint operators were detected) and are still inspectable. If the model or API rejects images, or cannot call tools to request them, the run fails with a lasting error asking the user to choose a vision-capable tool-calling model in Settings. There is no silent text-only retry or JSON fallback, and charts are not claimed as understood. The source dialog shows a rendered page image when the visual link is open, plus the extracted text. Rendered bytes stay in the side panel and are requested by the service worker one page at a time; they are never written to `chrome.storage` and are not copied into the worker as a whole document. |

## Verification boundary

The **probe** demonstrated native PDF → side panel → 4,434,082-byte HTTP PDF → local worker → three-page preview.
That is not browser acceptance of this production implementation. Unit tests now exercise a small real three-page PDF (unique English/Chinese markers, repeated sentences and two columns), a spacing fixture with mid-word font-change splits (`tradema`/`rks`, `re`/`sp`/`ective`) plus typographic word and column gaps, a password-protected PDF, a blank file (now accepted as image-only), a visual fixture whose chart fact is absent from the text layer, on-demand page rendering and inspect-tool budgets, the long-document notes path with `inspect_pdf_page`, bounded streaming, full-document chunking, navigation/user-action grants (including worker suspension and tab-specific side-panel options), and sidebar auto-read/auto-overview, cache reuse, cancellation, and source-page selection without panel-local storage writes. Activating an ordinary tab must not clear an in-memory PDF read.

Production Chrome acceptance still needs: normal webpage routing, PDF toolbar opening/no new tab, automatic local read and Overview on an authorized sidebar (cache, cancel, retry, missing-model guidance), all-page counts/source pages, theme and narrow sidebar, chat, and navigation/reload expiry. No browser was driven by shell, and the large original PDF was not fetched again during development.


## Test-only shortcut wake snapshot

`VITE_RP_ENTRY_DIAG=1 npm run zip` builds `entry-check.html` and bounded session breadcrumbs for the unresolved PDF shortcut reopening case. Normal builds contain neither the recorder nor this page. This is an observation build, not a speculative routing fix.

The test build records at most 80 events under `rp-entry-check-v1`: worker boot/main, listener readiness, receipt of the custom command, cached-PDF vs MIME branch, panel API resolution/rejection, normalized error code. Only timestamps, tab IDs, enums and booleans are stored; URLs, text, raw exceptions and grants are excluded. Writes are queued after the routing turn, never awaited by the action. There is no timer, polling, port, new event subscription, or intentional worker keepalive. In particular it does not subscribe to panel close/open events, which could otherwise wake the worker and mask this case. Brief session writes can still affect timing; they are not proof that instrumentation has no observer effect.

For one useful trial: load only this test build and bind its custom shortcut; open the PDF with the toolbar, close the side panel, close all worker DevTools and snapshot pages, allow the worker to become idle, focus the PDF canvas, and press the shortcut once. Only afterwards open `chrome-extension://EXTENSION_ID/entry-check.html`. The page reads session storage directly, once, without messaging the worker. Compare the command/boot/stage timestamps (shown in SGT). A missing command row alone does not prove whether Chrome dispatched it; compare the surrounding boot/readiness records and the earlier toolbar baseline. A received command identifies its branch and API outcome. `open-resolved` is only Chrome's API promise resolution, not a claim of visible UI. Return to the normal build to remove the instrumentation.
